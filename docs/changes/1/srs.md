# 软件需求规格说明（Software Requirements Specification，SRS）：完整、可追溯的 Agent 工作回顾

> 状态：已于 2026-10-02 获发起人认可（D1–D17 先获认可，D18 及相应修改随后单独获认可）。
> 来源：[Issue #1](https://github.com/Eridanus117/agent-activity-report/issues/1) 的目标与十条边界；2026-10-02 需求讨论中项目发起人逐轮答复并确认的已定事项清单；同日在 Windows 本机完成的限定原型（`prototype/proto.ts`，产出留在仓库之外）。
> 原始讨论与原型产出含私人会话内容，不公开；本文只引用不含会话内容的方法、数量和结论。

## 问题

使用者想知道自己和 Agent 在选定的一天里做了什么、作出了什么决定、还有什么没做完。这些信息散在多个 Agent 会话记录里，逐篇回看不现实。

执行 Agent 不应为了这份回顾写日记、填字段或重复汇报。回顾由独立程序事后读取现成的会话记录生成，完整性优先于及时性。

使用环境是 Windows 和 macOS。发起人在 macOS 上只使用 omp，在 Windows 上使用 Claude Code 和 omp。

## 方案

一个命令行程序，对指定的一个自然日运行一次：

1. 只读地盘点受支持客户端的会话记录，逐条按时间戳选出当天的记录，并记下每个文件的处理状态。
2. 把选出的记录压成一份较小的摘录：对话文字保留全文，工具调用压成一行，成功的工具输出不带。
3. 把摘录分块交给模型，模型逐块抽出带记录引用的事件。
4. 程序校验每个事件的引用，并依据引用的类型判定证据等级。
5. 模型把事件跨会话归并成事项，再从事项写出概览。
6. 程序输出概览、事项明细和覆盖清单。

原型在一台机器、一天、一个来源（omp）上跑通了这条路径：扫描 742 个记录文件，当天有记录的主会话 6 个，摘录约 54 万字符（实测约 24 万 token，约为当天会话文本总量的 7%），一遍耗时约 3 分钟，按所用模型的目录价约 0.03 美元。

## 场景

1. 使用者对昨天运行程序，得到一份概览和一份事项明细，明细里每个事件都能定位到原始记录的文件和行。（D3、D9、D14）
2. 一个会话从前天开到昨天凌晨：只有时间戳落在昨天的记录进入昨天的报告。（D3）
3. 当天还用了不受支持的客户端：报告明确写出哪些来源没有覆盖，不让读者以为报告涵盖了所有工作。（D1、D4）
4. 某个记录文件读不出来，或某次模型调用失败：报告照常生成，并写明哪些文件或会话没有进入报告。（D4、D5、D12）
5. Agent 在回复里说「已完成」，但没有成功的工具调用支撑：事件标为「仅 agent 自述」，不标为有证据。（D11）
6. 模型回复里出现记录中不存在的引用，或某一行格式损坏：该事件被拒并记入覆盖清单，其余事件不受影响。（D9、D10）
7. 使用者发了一条消息，但没有任何事件引用它：覆盖清单列出这条消息的位置，供人查看是否漏项。（D4）
8. 程序运行后，来源目录里没有因为这次运行多出新的会话记录。（D8、D16）

## 定下的事

### 来源与读取

- **D1 首批支持的来源是 omp 和 Claude Code。** 其他客户端（包括 Codex CLI）不读取；报告和覆盖清单必须写明受支持的来源只有这两个，其余来源未覆盖。
  依据：发起人答复「macOS 只使用 omp，win claude + omp，codex cli 很少用」；Issue 边界 6。
  例：只启用 omp 的一次运行，覆盖清单的未支持来源一项列出 Claude Code、Codex 及其他客户端。
  Claude Code 记录的具体映射未提供，见「未定」。

- **D2 来源位置按客户端的默认存放位置相对用户主目录解析，并可由使用者覆盖。** 程序不写死某台机器的绝对路径。
  依据：Issue 边界 10。
  例：omp 的会话记录在用户主目录下的 `.omp/agent/sessions/`，其下每个工作目录一个子目录；主会话是该子目录下的一个 JSONL 文件，子 agent 的记录在以主会话命名的下级目录里（原型观察到两级嵌套）。

- **D3 「一天」是运行机器本地时区的自然日，逐条记录按自身时间戳归属。** 不依据文件名或文件修改时间；跨午夜的会话按记录切开。
  依据：发起人确认的已定事项第 6 条；Issue 首个验收场景第 1 条。
  例（边界两侧）：本地时间 23:59:59.999 的记录属于当天；00:00:00.000 的记录属于次日。
  例：原型中 10-01 的报告包含了 09-29 和 09-30 开始、延续到 10-01 的会话里属于 10-01 的记录。
  没有时间戳的记录（例如 omp 文件首行的标题记录）不归入任何一天，按文件计数写入覆盖清单。

- **D4 每次运行输出一份覆盖清单**，至少包含：
  - 所选日期、所用时区、所用模型；
  - 受支持的来源和未支持的来源；
  - 扫描的文件总数；
  - 每个当天有记录或出现问题的文件：读取状态、记录数、当天记录数、无法解析的行数、无时间戳的记录数、各类记录送入或未送入的数量；
  - 每次模型调用：对应的会话、送入字符数、耗时、状态；
  - 被拒的事件及原因；
  - 未被归入任何事项的事件数、被归入多个事项的事件数；
  - 每个主会话里未被任何事件引用的用户消息的位置。
  依据：Issue 边界 6；发起人确认的已定事项第 16 条；原型结论（未被引用的用户消息这一项暴露了长输入少抽的问题）。
  例：原型不分块的一遍里，全天 88 条用户消息有 55 条被引用；分块后为 78 条。

- **D5 读取问题不得悄悄跳过。** 文件读不出来时记录为读取失败并继续处理其余文件；无法解析的行按文件计数。Windows 上路径超过 260 字符的文件必须能读取。
  依据：Issue 边界 6；盘点时一个超长路径曾导致扫描脚本整体中断。
  例：路径长度 300 字符的记录文件 → 正常读取。一行不是合法 JSON → 该文件的无法解析行数加一，其余行照常处理。

### 送什么给模型

- **D6 摘录规则**（以 omp 记录为准；Claude Code 的对应规则见「未定」）：

  | 记录内容 | 处理 |
  |---|---|
  | 用户消息 | 全文 |
  | 助手的文字回复 | 全文 |
  | 工具调用 | 一行：工具名、意图、对象、结果（成功 / 报错 / 无结果） |
  | 报错的工具输出 | 取头尾各一段，标明省略长度 |
  | 成功的工具输出 | 不送 |
  | 向用户提问及用户的回答 | 问题和回答都送 |
  | 待办变更 | 送 |
  | 会话退出、模型报错、助手中止 | 送 |
  | 子 agent 会话 | 收到的任务、文字回复送；工具调用同样压成一行 |
  | 思考过程 | 不送 |
  | 会话内的上下文压缩摘要 | 不送内容，只留一个发生过压缩的标记 |
  | 其他记录类型 | 不送，按类型计数写入覆盖清单 |

  依据：发起人「重点其实是发生了什么，还有那些决策信息，以及进度信息」；Issue 边界 8（不以摘要代替原始记录）；原型按此规则产出的报告经发起人查看后认可。
  例：一次成功的读文件调用 → 一行，含文件路径和「成功」。一次报错的命令调用 → 一行加报错输出的头尾。
  各项截断长度的具体数值未提供，见「未定」。

- **D7 摘录按约 6 万字符分块送入，块大小可配置。**
  依据：原型中同一个会话一次送入 27 万字符时抽出 5 个事件、引用 35 条用户消息中的 5 条；按 6 万字符分块后抽出 124 个事件、引用 31 条。
  块边界处的上下文如何处理未提供，见「未定」。

### 模型调用

- **D8 模型经本机已登录的 omp 以非交互方式调用。** 默认模型 `gpt-6-luna`，模型可配置，允许使用 omp 接入的第三方提供商。调用不保存会话，并关闭工具、技能、规则和扩展；标准输入必须关闭。
  依据：发起人选定经已登录 CLI 调用、「就用 luna」、「甚至允许 omp + 第三方服务提供商」；原型验证了该调用方式下来源目录的记录文件数不变；标准输入不关闭时 omp 的非交互模式会挂起。
  例：一次运行前后，omp 会话目录下的 JSONL 文件数相同。

### 拿什么回来

- **D9 模型逐块输出事件，每行一个独立的 JSON 对象。** 每个事件包含：
  - 类型：请求、调整、决定、探索、完成、失败、取消、阻塞、未完成之一；
  - 一句陈述；
  - 行为人：用户或 agent；
  - 模型给出的证据等级：计划、尝试、有证据；
  - 至少一个记录引用；
  - 时间。
  依据：Issue 边界 4、5；原型中要求输出单个 JSON 对象时，两遍各有一到两个会话因一处格式错误整体作废，改为每行一个事件后只损失坏掉的那一行。

- **D10 程序校验每个事件。** 没有引用、引用了摘录中不存在的记录、或该行无法解析的事件被拒，连同原因写入覆盖清单，不进入报告。
  依据：Issue 边界 5；发起人确认的已定事项第 12 条。
  例（边界两侧）：引用全部存在 → 接受；其中一个引用不存在 → 拒绝。

- **D11 agent 事件的证据等级由程序依据引用类型复核。** 模型标为「有证据」的 agent 事件，其引用中至少要有一条是成功的工具调用、用户消息、用户对提问的回答或用户的待办编辑；否则改标为「仅 agent 自述」。用户的事件不显示证据等级。
  依据：Issue 边界 5；原型第一遍 102 个事件里 98 个被模型标为有证据，加上此规则后 agent 事件为 89 个有证据、22 个尝试、15 个仅自述。
  例（边界两侧）：「完成」事件引用了一条成功的命令调用 → 有证据；只引用了助手的文字回复 → 仅 agent 自述。

- **D12 模型调用失败或回复中没有任何可用事件时，该块对应的会话必须在概览的覆盖部分点名**，说明其内容未进入报告。
  依据：Issue 边界 6；原型第一遍中最大的会话调用失败，报告据此标出。

- **D13 事件跨会话归并成事项，概览只依据事项和事件写成。** 每个事件要么属于一个事项，要么列在明细的「未归并事件」下；不得丢弃。归并出的事项引用了不存在的事件编号时，该引用被拒并记入覆盖清单。
  依据：Issue 边界 3、7；发起人确认的已定事项第 14 条。
  例：原型分块的一遍，230 个事件归入 6 个事项，未归并 0 个。
  归并粒度和事项状态如何判定未提供，见「未定」。

- **D14 输出三份文件：** Markdown 概览、Markdown 事项明细、JSON 覆盖清单。概览含覆盖情况、总述和事项列表；明细按事项列出状态、小结、遗留事项和事件时间线，每个事件给出来源文件和行号。
  依据：Issue 边界 3、5；发起人确认的已定事项第 15 条。

### 实现与边界

- **D15 实现语言是 TypeScript，运行时是 Bun。**
  依据：发起人把选择限定在 TypeScript 与 Go/Rust 之间并交由 agent 选定；omp 经 Bun 安装，使用 omp 的机器通常已有 Bun。macOS 上的实际情况未验证。

- **D16 程序对来源只读。** 不修改、不回写、不新增任何会话记录。
  依据：Issue 边界 2。

- **D17 真实会话、摘录、模型调用的输入输出和生成的报告不进入本仓库。** 仓内测试数据从零构造。本机真实数据可用于本地实验，产出留在本仓库之外。
  依据：Issue「数据与公开边界」；发起人授权在 Windows 本机用真实的一天跑原型；本仓库是公开仓库。
  原写：Issue 中 Windows 只使用合成数据、真实数据实验在 macOS。发起人 2026-10-02 授权 Windows 本机原型后，改为上述表述。

- **D18 报告写入使用者配置的输出目录，程序不做提交和推送。** 输出目录可以是一个 Git 仓库的工作副本；是否提交、推送到哪里由使用者自己处理。每台机器各自配置、各自保存，报告不跨机器汇集。
  依据：发起人希望报告能存进仓库长期保留；Windows 的报告存入一个新建的私有仓库；macOS 的报告不上 GitHub，由发起人存到那台机器可用的其他版本库；发起人对「程序只写目录」的推荐答复「全按推荐」。
  例：Windows 上输出目录指向私有报告仓的工作副本 → 程序写入三份文件后结束，工作副本里出现未提交的改动，没有新的提交。

## 测试决定

- **层次**：在读取、摘录、校验、证据判定和渲染这几层的导出函数上测，输入是从零构造的合成记录文件；模型调用层在测试里替换为返回固定文本的替身，不在自动测试中调用真实模型。
- **边界**：D3 午夜两侧；D5 的超长路径（仅 Windows）、坏行和读取失败；D7 块大小两侧；D10 引用存在与不存在、坏行；D11 有无成功工具调用支撑；D12 调用失败；D13 未归并事件和不存在的事件编号。
- **先例**：仓内目前没有代码和测试框架，没有先例；按 D15 使用 Bun 自带的测试运行器。
- **验收**：首个验收场景是 macOS 上真实一天的 omp 样报。语义漏项核对只在开发验收时做一次，方法是用更强的模型逐会话独立核对，再由发起人抽查；结论里把模型核对过的和人抽查过的分开写。少量语义漏项可以接受；覆盖清单（D4）不放宽。该核对不做成产品功能。
  依据：发起人「这个只是在开发的时候去做一次核对，以后就不用核对了，而且漏一点其实问题也不大的」。
- Windows 与 macOS 的读取和路径行为用合成数据检查。

## 不在范围

- 界面、通知推送、定时调度、小时级刷新。（Issue 边界 9）
- 要求执行 Agent 写日志或调用本工具。（Issue 边界 1、2）
- Codex CLI 及其他客户端的读取。（发起人：很少用）
- 直连模型 API、本地模型。（发起人选定经已登录的 CLI 调用）
- 把成功的工具输出全文送给模型。（原型显示不送已能产出可读的报告；发起人「先试试」收窄方案）
- 把语义漏项核对做成常规功能。（发起人：只在开发时核对一次）
- 程序自动提交或推送报告。（发起人按推荐选定只写目录）
- 多日或任意时间范围的报告。（首个验收场景是一天；其他范围未讨论）

## 未定

- **Claude Code 记录的摘录规则**：主会话、子 agent、工具结果文件、续接和迁移记录如何对应 D6。不定它，D1 中 Claude Code 的支持无法实现。
- **归并粒度与事项状态的判定方法**：原型里一个事项并入了 124 个事件，同一事项在两遍运行里分别被判为进行中和已完成。不定它，D13 的输出质量不稳定。
- **块边界的上下文处理**：一件事跨两块时，后一块缺少前文。不定它，分块可能造成事件割裂或漏抽。
- **D6 各项截断长度**（工具调用行、报错输出头尾、子 agent 任务等）：缺数。原型用的数值只是试验值。
- **未支持来源是固定列出，还是探测本机实际存在哪些客户端后列出**：不定它，D1 的「未覆盖」说明只能写成固定文字。
- **未配置输出目录时的行为，输出目录内按日期如何组织，以及是否拒绝写入本工具自己的代码仓库**：输出去向已定，见 D18；这三点不定，D14、D17 的默认行为不明确。
- **摘录和模型调用的输入输出是否随报告一起保存**：它们比报告更接近原始会话内容。不定它，D18 的输出目录里放什么不明确。
- **读取中断后的恢复、对同一天重复运行时的行为**：Issue 列为待定契约，本轮未讨论。
- **模型调用失败后是否自动重试、重试几次**：缺数。
- **命令行的参数形式**：未讨论。
- **macOS 上 omp 的版本、安装方式、记录格式是否与 Windows 一致，以及可用的模型**：需在那台机器上核实。不核实，D2、D8、D15 在 macOS 上是否成立未知。
- **验收时「更强的模型」用哪一个、发起人抽查多少个会话**：缺数。
- **未被引用的用户消息达到多少算不合格**：缺数；目前只列出，不设阈值。
