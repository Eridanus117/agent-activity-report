# 软件设计说明（Software Design Description，SDD）：完整、可追溯的 Agent 工作回顾

> 状态：已于 2026-10-02 获发起人认可。
> 依据：SRS `docs/changes/1/srs.md`（D1–D18 及「未定」一节）。
> 本文对 SRS「未定」中属于设计的条目给出方案。凡标「未经原型验证」的内容是设计推断，不是已观察到的行为。

## 现状与改后的结构

现状：仓内没有正式代码。`prototype/proto.ts` 是一个单文件原型，只支持 omp，读取、摘录、调用模型、校验、渲染都写在一起；它不作为正式实现沿用。

改后分为下列模块，数据单向流动：

```
来源适配器（omp / Claude Code）
   └─> 统一记录 ─> 按天筛选与去重 ─> 摘录 ─> 分块
                                               └─> 事件抽取（模型）─> 校验与证据判定
                                                                        └─> 事项归并（模型）─> 状态判定 ─> 渲染
覆盖台账：贯穿以上每一步，最后写成覆盖清单
模型运行器：被「事件抽取」和「事项归并」调用，封装对 omp 的非交互调用
```

- **来源适配器**：每个客户端一个。负责找到记录文件、逐行读取、把客户端特有的记录翻译成统一记录。只有这一层知道客户端的格式。
- **按天筛选与去重**、**摘录**、**分块**、**校验与证据判定**、**状态判定**、**渲染**：纯函数，不接触文件系统和模型，是自动测试的主要对象（SRS「测试决定」）。
- **模型运行器**：唯一会启动外部进程的模块；测试中替换为替身。
- **覆盖台账**：各步骤往里记数和记问题，不参与决策。

## 接口与数据形状怎么变

全部为新增。

### 统一记录

适配器对每一行原始记录输出一条统一记录：

| 字段 | 含义 |
|---|---|
| `source` | `omp` 或 `claude-code` |
| `session` | 主会话标识；子 agent 的记录归到它所属的主会话 |
| `file`、`line` | 相对来源根目录的文件路径和行号，用于来源定位 |
| `id` | 客户端给这条记录的标识，没有则为空 |
| `timestamp` | 记录时间，没有则为空 |
| `subagent` | 是否来自子 agent 的记录文件 |
| `kind` | 见下表 |
| `text` | 送入摘录的文字（已按规则截断） |
| `tool` | 仅工具调用：名称、意图、对象、结果（成功 / 报错 / 无结果）、报错输出的头尾 |
| `rawType` | 原始记录类型，供覆盖清单按类型计数 |

`kind` 的取值和证据判定中的作用：

| `kind` | 是否送入摘录 | 能否支撑「有证据」（SRS D11） |
|---|---|---|
| `user`（用户消息） | 送 | 能 |
| `ask`（向用户提问及回答） | 送 | 能 |
| `todo_edit`（用户编辑待办） | 送 | 能 |
| `tool`（成功或无结果的工具调用） | 送一行 | 仅结果为成功时能 |
| `tool_error`（报错的工具调用） | 送一行加报错头尾 | 不能 |
| `assistant`（助手文字） | 送 | 不能 |
| `subagent_task`（子 agent 收到的任务） | 送 | 不能 |
| `stop`（退出、中止、模型报错） | 送 | 不能 |
| `marker`（如发生过上下文压缩） | 只送标记 | 不能 |
| `skipped`（其余） | 不送，只计数 | — |

原型把「无结果」的工具调用也算作可支撑证据，这里收紧为只有成功才算。

### 适配器接口

- `locate(root?)`：返回该来源的记录文件列表和默认根目录；根目录不存在时返回「该来源在本机不存在」，不算错误。
- `read(file)`：返回统一记录序列，以及坏行数、读取错误。读取错误不抛出，交给覆盖台账。

**omp 映射**（已由原型验证）：按 SRS D6 的表。主会话是工作目录子目录下的 JSONL 文件，子 agent 记录在以主会话命名的下级目录中，可多级嵌套。

**Claude Code 映射**（未经原型验证；依据是对本机近期记录的字段统计）：

| 原始记录 | 统一记录 |
|---|---|
| 主会话文件；`subagents/` 下的 JSONL | 主会话记录；子 agent 记录（`subagent` 为真） |
| `user`，内容为文字，非 `isMeta` | `user` |
| `user`，内容为 `tool_result` | 不单独成记录，按 `tool_use_id` 并入对应的工具调用，`is_error` 决定成功或报错 |
| `assistant` 的文字块 | `assistant` |
| `assistant` 的 `tool_use` 块 | `tool` / `tool_error`；向用户提问的工具归为 `ask`，启动子 agent 的工具其参数归为 `subagent_task` |
| `assistant` 的思考块 | `skipped` |
| `assistant` 带接口报错或中途中止标记 | `stop` |
| `pr-link` | `tool`（成功），文字为 PR 仓库和编号 |
| `system` 中的离开期间摘要、`attachment`、`queue-operation`、各类无时间戳的状态记录 | `skipped` |
| `tool-results/` 下的文件、`subagents/` 下的 JSON 元数据、会话目录里的其他文件 | 不读取，按扩展名计数写入覆盖清单 |

三处需要在实现时先用小原型核实，核实前不声称 Claude Code 已支持：
1. `user` 记录的文字里混有客户端注入的内容（提醒、命令输出说明等），怎样只留下用户真正输入的部分。
2. 排队的用户消息（`queue-operation` 和 `queued_command` 类附件）是否会以普通 `user` 记录再出现一次；如果不会，它们需要改为送入。
3. 恢复或分叉会话时，旧记录是否会被复制进新文件。

### 按天筛选与去重

- 筛选按 SRS D3。
- 去重：同一来源内 `id` 相同的记录只保留先遇到的一条，重复数写入覆盖清单。omp 记录未观察到跨文件重复；这一步主要为 Claude Code 的上面第 3 点预留。

### 分块

- 只在主会话的用户消息之前切分，使一块包含若干完整的「用户消息及其后续」。一段超过块大小时才在段内按行切。
- 同一会话的各块顺序处理。从第二块起，在摘录前附上本会话此前已抽出的事件陈述列表，并说明这些只作背景、不要重复输出。
- 不同会话之间并行，默认 4 路。

### 模型运行器

- 输入：一段提示词文本和模型名。输出：回复文本、耗时、状态（成功 / 调用失败）。
- 调用方式按 SRS D8。
- 调用失败或回复中没有任何可用行时自动重试 1 次；仍失败则按 SRS D12 处理。
- 以「提示词内容加模型名」的摘要为键，把成功的回复缓存在工作目录。同一天重跑时命中缓存的调用不再发出；这同时就是读取中断后的恢复方式。来源记录有变化时摘录随之变化，自然不命中。

### 事件与事项

事件（程序校验后）：SRS D9 的字段，加上程序赋予的编号、所属会话，以及复核后的证据等级（计划 / 尝试 / 有证据 / 仅 agent 自述）。

事项归并分两步：

1. **模型只做分组**。输入是全部事件的编号、会话、时间、类型和陈述；输出每行一个事项：标题、小结、所含事件编号、遗留事项。模型不输出状态。
2. **程序判定状态**，只看该事项内事件的类型、证据等级和时间顺序：

   | 条件（自上而下取第一条满足的） | 状态 |
   |---|---|
   | 时间最晚的「取消」之后没有「完成」 | 已取消 |
   | 存在「阻塞」，其后没有「完成」 | 阻塞 |
   | 存在「未完成」，或最晚的「失败」之后没有「完成」 | 进行中 |
   | 存在证据等级为「有证据」的「完成」 | 已完成 |
   | 存在「完成」，但都不是「有证据」 | 自述完成，无证据 |
   | 其余 | 进行中 |

归并提示词要求一个事项对应一件可独立交付的工作或一个独立的问题，同一会话通常产生多个事项。覆盖清单记录最大事项所含事件占全部事件的比例，供人判断是否并得过粗；不设自动阈值。

### 输出与工作目录

- 命令行：`--day <YYYY-MM-DD>`（必填）、`--out <目录>`（必填，或由配置文件提供）、`--source`（默认全部受支持来源）、`--model`、`--chunk`。没有输出目录时报错退出，不猜默认位置。
- 输出目录下每天一个子目录 `YYYY-MM-DD/`，内含 `overview.md`、`items.md`、`coverage.json`。同一天重跑时覆盖这三份文件；旧版本由使用者的版本库保留。
- 输出目录位于本工具自己的代码仓库之内时拒绝运行。
- 摘录、提示词和模型回复只写入工作目录（默认在操作系统的用户缓存目录下），不进入输出目录。
- 截断长度采用原型的数值作为初始默认值并可配置：工具意图 100 字符、命令 160、报错输出头尾各 300、提问及回答 1500、子 agent 任务 1500、待办 500 至 800。
- 未支持来源：程序探测一组已知客户端的默认记录目录，存在的列为「检测到但未支持」；同时固定写明「其余客户端不在检测范围」。首版探测 Codex CLI。

## 取舍表

### 事项状态由谁判定

| 候选 | 支持 | 反对 | 最大风险 | 可逆性 |
|---|---|---|---|---|
| 模型判定（原型做法） | 实现最简单 | 原型中同一事项两遍运行结果不同 | 把没做完的写成已完成 | 高 |
| 程序按规则判定（本文采用） | 同样的事件必得同样的状态；规则可测试 | 规则表达不了的情况会被归入「进行中」 | 事件类型抽错时状态跟着错 | 高：改回模型判定只动一个模块 |

暂定推荐：程序按规则判定。会推翻它的事实：macOS 验收核对发现规则判错的比例高于模型判定。

### 块边界的上下文

| 候选 | 支持 | 反对 | 最大风险 | 可逆性 |
|---|---|---|---|---|
| 不处理（原型做法） | 各块可并行，最快 | 一件事跨块时被割裂 | 后一块把延续的工作当成新请求 | 高 |
| 相邻块重叠若干行 | 简单 | 重叠区的事件会被抽两次，需要去重 | 重复事件 | 高 |
| 在用户消息处切分，并附上此前事件的陈述（本文采用） | 块内语义完整；后续块知道前文 | 同一会话的块只能顺序处理，变慢；提示词变长 | 模型把背景事件重新输出一遍 | 高 |

暂定推荐：第三种。未经原型验证。会推翻它的事实：背景列表导致重复输出明显增多，或耗时不可接受。

### 中断恢复

| 候选 | 支持 | 反对 | 最大风险 | 可逆性 |
|---|---|---|---|---|
| 不恢复，每次整天重跑 | 无状态 | 一次失败就重付全部调用 | 额度浪费 | 高 |
| 按提示词内容缓存模型回复（本文采用） | 重跑只补缺的；不需要单独的进度文件 | 工作目录里留有会话摘录的派生内容 | 缓存目录被误当成可公开内容 | 高：删目录即可 |

暂定推荐：按内容缓存。会推翻它的事实：使用者不接受工作目录里留存这些内容。

---

本文未涉及：验收时用哪个更强的模型、抽查多少会话、未被引用的用户消息多少算不合格（SRS「未定」中的三个缺数项），以及 macOS 上的环境核实。它们不影响结构，留到验收安排时定。
